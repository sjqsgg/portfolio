# Project content rules

Confirmed: 14 September 2026. Applies to the English portfolio project viewer. These decisions supersede earlier conversation proposals for Problem / Approach / What I learned sections.

## Layout and fields

- Keep the existing project viewer: concise information on the left, large project visuals and optional chapter thumbnails on the right.
- Use one circular return control. Project details return to All projects; the project index returns home.
- The optional label above the title describes project type (Personal project or Company project), not progress.
- Keep title and a concise summary explaining what the project does and whom it serves.
- Keep Category, Role, Status and Year. Role describes the owner's actual contribution, especially when extending an existing system. Status describes progress; Year uses verified dates or a date range.
- Keep optional, expandable Project notes. Write natural paragraphs; do not impose Problem, Approach or What I learned headings. Notes may explain motivation, choices, context or verified response without repeating the summary.
- Show GitHub, demo or video links only when available and verified. Do not require every project to have every link.
- Use actual screenshots, posters or demo frames. Captions explain the selected visual. Show thumbnails only when multiple meaningful assets exist; there is no required chapter count.
- Community metrics can appear in notes. Distinguish stars, combined likes and saves, and actual users. Do not invent dates, outcomes, personal reflections or assets.
